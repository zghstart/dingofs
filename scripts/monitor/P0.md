# P0 observability baseline

This implements the P0 parts of the Feishu DingoFS 5.3 observability plan
(OBS-01/02/05 and existing-source portions of 04/07/10/11/13/15/17/18/19/21).
The initial source base is `3cd6bfc1c`; CMake still calls this code 5.1.0.
The 5.3 release must freeze its own implementation SHA and repeat acceptance.

## What is delivered

- Synchronous GET counts the returned string size after completion. Asynchronous
  GET counts `actual_len`, including successful short reads. Failed reads do not
  add successful bytes. Requested inflight bytes remain independently balanced.
- Discovery distinguishes nonzero exit, timeout, malformed/empty JSON, invalid
  structure and business error from a successful empty list. Snapshots and error
  counters are persisted per component. A failed component retains its last
  success for a configurable period; successful empty lists remove targets.
- Operator-owned expected inventory is independent of discovery. Disappearing
  targets remain detectable after retention expires. Old file_sd data is migrated
  as **unverified** retained data, with `last_success=0`, never as fresh success.
- Targets keep the old `job=client|mds|remotecache`, add `cluster/component/node`,
  and retain Prometheus `instance=host:port`. Client `fs_id` comes from mount
  discovery, with conflict checks. No path, inode, PID or request ID labels.
- Numeric cache health/running companions preserve legacy string `/vars` fields.
  Recording rules emit fixed one-hot states. Missing or failed samples become unknown using disk identities retained for
  five minutes; identities outside that window remain absent.
- Seven additional dashboards cover overview, client, MDS, cache, storage backend,
  capacity/quota, and host/runtime. The three legacy dashboards are retained.
  Overview includes stable Client/FS Top Actors and the configured inventory table.
  This table is topology/identity information, **not measured Data Flow**.
- Existing warmup gauges, callback results, backpressure and quota snapshots are
  included. Pool allocation hits are not represented as data-cache hits.
- Collection-quality alerts detect scrape failure, removed expected targets,
  discovery failure/staleness and persistence failure.

## Configure discovery

Edit `target.ini` from the monitor working directory:

```ini
[path]
target_path=prometheus/data/targets.json
state_path=prometheus/data/discovery-state.json
inventory_path=prometheus/expected-targets.json

[discovery]
cluster=my-cluster
interval=60
timeout=5
retention_seconds=3600
metrics_listen=127.0.0.1:19100
```

`targets.json` is generated. `expected-targets.json` is maintained by the operator
and must not be replaced with the output of a discovery attempt:

```json
[
  {"targets":["192.0.2.10:7801"],"labels":{"cluster":"my-cluster","component":"mds","node":"meta-1"}},
  {"targets":["192.0.2.20:10000"],"labels":{"cluster":"my-cluster","component":"client","node":"worker-1","fs_id":"42"}},
  {"targets":["192.0.2.20:9300"],"labels":{"cluster":"my-cluster","component":"cache","node":"worker-1"}}
]
```

Each instance gets its own target, including multiple mounts on one host. The
inventory provides stable node aliases; unlisted target identities fall back to
advertised host. Add new nodes/mounts to independent inventory to make removal
alerts and cross-port host correlation complete. Restart discovery after inventory
changes. Remove intentionally retired targets explicitly, and silence approved
maintenance in Alertmanager by cluster/component/instance or target.

```bash
python3 target_json.py --show --count 1   # nonzero exit if any component fails
python3 target_json.py                  # normal continuous operation
```

The HTTP listener serves **discovery health only**; application metrics continue
on `/brpc_metrics`. A process lock prevents concurrent writers for the same state.
The health endpoint stays responsive during command timeouts. Do not delete state
to repair a command/network failure. Back up state and targets before migration.
Discovery freshness rules use 180 seconds for the default 60-second interval;
review that threshold when changing the interval.

## Deploy all monitoring hosts

The accompanying dingocli changes make `node_exporter.deploy` authoritative for
host coverage, including client/cache hosts outside the metadata topology. All
hosts must already be registered in `dingo hosts`; unknown/ambiguous hosts fail
before deployment. Explicit central service `deploy` lists are honored.
Node file_sd groups include stable `cluster/node/component=host` labels. Keep the
same node identities in application expected inventory. Actual `instance` ports
are preserved. The sync script updates `node-targets.json` atomically and is
idempotent; it does not append duplicate scrape jobs.

For an existing Ansible-managed stack, use the reviewed CLI and supply:

```yaml
dingo_monitor_observability_assets_dir: /path/to/dingofs/scripts/monitor
dingo_monitor_expected_targets: # independent inventory as above
  - targets: ["192.0.2.10:7801"]
    labels: {cluster: my-cluster, component: mds, node: meta-1}
```

The overlay stages and validates inventory and Prometheus before installing live
configuration. It renders the cluster identity and selected ports, and restarts
only monitoring services whose configuration changed. An omitted expected-inventory
replacement preserves the existing operator list. It preserves TSDB data and
legacy dashboards. Its fixture tests cover validation failure and rerun behavior.
The asset overlay is explicitly enabled by the source path; normal role check
mode skips application. A fresh server image should ship this monitor directory.

A second, deterministic `DingoFS Prometheus` datasource is used by the P0 boards;
the legacy `Prometheus` datasource is retained. Regenerate boards with:

```bash
python3 generate_dashboards.py
```

## Metric interpretation contract

| Source | Semantics | Safe use |
| --- | --- | --- |
| `*_qps_total_count`, `*_bps_total_count` | Monotonic successful requests/bytes | `rate`; not all completed outcomes |
| `*_error_num`, `*_eps_total_count` | Cumulative failures | Error denominator is successes + failures |
| `*_qps`, `*_bps` | Window rates | Plot directly; never rename to counter and rate again |
| `*_lat_total_value` | Cumulative successful latency in microseconds | `rate(lat_total)/rate(success_count)/1e6` |
| LatencyRecorder window/quantile | Per-instance window statistics | Keep instance; never average p99 into cluster p99 |
| Six `block_*_num` values | Inflight gauges | Plot directly; must fall back after completion |
| Disk/remote hits and misses | Conditional same-tier counters | Same-window hit/(hit+miss); idle is N/A |
| `remote_cache_cluster_*` | Canonical remote byte counters | Exclude `remote_node_group_*` aliases from sums |
| `vfs_*pressure*_num` | Existing cumulative pressure events | Actual source has `vfs_`, not `dingofs_vfs_` |
| Six warmup queue/inflight values | Gauges | Direct values, not rate |
| Warmup callback success/failure | Cumulative block callbacks | Success/Exist does not prove cached data is ready |
| `fs_quota_*` | Per-MDS replica snapshot | Keep instance; no replica sum or authoritative ratio |
| Health code / running code | Gauge: 0/1/2/-1 or 0/1/-1 | Normalized to fixed state labels by recording rules |

Source `# TYPE` and semantic type are recorded separately: PassiveStatus can export
a monotonic underlying counter as a gauge. Names, units, reset behavior and event
boundaries require code **and runtime** evidence. No histogram, business error
labels, backend identity or quota authority is inferred from a metric name.

## Verification and evidence

```bash
python3 -m unittest discover -s scripts/monitor/tests -v
promtool check config scripts/monitor/prometheus/prometheus.yml
# For the container layout, mount prometheus/ at /etc/prometheus and its data/
# at /prometheus before checking the production configuration.
cd scripts/monitor/tests && promtool test rules rules.yml
```

`collect_contract.py` saves actual `/brpc_metrics` and `/vars` responses,
Content-Type, SHA256, metric names and exported types, plus optional client .stats.
Keep samples in the task evidence directory outside Git; they can contain
operational details. It deliberately does not mark runtime acceptance complete:
that requires known workload increments, failures, resets and dashboard review.

```bash
python3 scripts/monitor/collect_contract.py \
  --source-sha IMPLEMENTATION_SHA \
  --target client=http://127.0.0.1:10000 \
  --target mds=http://127.0.0.1:7801 \
  --target cache=http://127.0.0.1:9300 \
  --client-stats /dedicated/test-mount/.stats --output-dir /task/evidence
```

For each deployment, record binary/dependency revisions, build flags, all three
samples, finite/idle/missing states, a controlled failure, reset/retention behavior,
query results and resource costs. `promtool` success, empty query results and
Grafana provisioning alone are not workload acceptance. Alert delivery requires
an actual Alertmanager route; no notification destination is configured here.

## P1 boundary

Business result classification, real aggregatable histograms, asynchronous write
stages, logical/attempt/SDK retry attribution, final cache decisions/actual Data
Flow, authoritative quota freshness, reactor scheduling and persistent business
SLI probes remain P1. S3/RADOS backend-specific and hardware capability acceptance
requires those environments. Do not represent an unsupported/unverified source
as zero or reuse a sample from another backend as evidence.

## Matched workflow and tested contract

The machine-readable family contract is [contracts/p0.json](contracts/p0.json).
The successful reference [Release run 43842197449](https://github.com/dingodb/dingofs/actions/runs/43842197449)
built source `3cd6bfc1cb7683bcb5c1077fb7071de7b285cab4`. Its build environment was
`dingodatabase/dingo-eureka@sha256:effb3a47159942b43f81d885edf371dc8be487836344d8d5e21d839eb6980548`,
with dingo-sdk `1d6c98788531ab7fb1112b39d6447d0b221fa6cb`. Match both when reproducing
this baseline; the workflow cache key also includes the SDK build-recipe hash.
The same run publishes `dingodatabase/dingofs:3cd6bfc` and `latest`; maintenance
branches publish branch-prefixed tags. Validate the immutable source revision,
not just a mutable `latest` tag or a mirrored repository name.

Runtime tests use a dedicated filesystem with dummy metadata and a local-file
backend. Source samples, controlled increments, counter reset, failed scrapes and
independent expected-target removal were exercised. Full backend/hardware and
release gates remain as listed in the contract. Cache runtime tests require
io_uring to be allowed by both the host and container policy.

MDS cache `fs_id/cache/event` labels are extracted only from a constructor-verified
source-name whitelist. Discovery's dedicated file_sd target carries collector
cluster/node identity; `honor_labels` is enabled only for this trusted collector
because its explicit inventory samples describe other components and nodes.
Standalone deployments must configure `prometheus/data/discovery-targets.json`
alongside `target.ini`; the paired CLI and Ansible overlay generate it.
